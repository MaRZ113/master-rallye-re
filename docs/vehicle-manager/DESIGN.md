# Vehicle Manager — installing vehicles without baking them into loaders

Status: DESIGN (11 November 2026), owner review requested. Supersedes the
"installable DLL" open question in DLL_EXTERNAL_RESOURCE_DEPLOYMENT.md.

## Goal

The player installs, removes and orders vehicles with a separate tool (the
Vehicle SDK "Vehicle Manager"). The game loaders (`dinput8.dll` single release
loader, `d3d8.dll` renderer) contain **no vehicle-specific code or data** and do
not change when the vehicle set changes. Removing all vehicles returns the game
to stock without touching any loader.

## Architecture

```
Vehicle Manager (Vehicle SDK tool)          dinput8.dll (generic, no car data)
  packages/*.mrcar  ──┐                       DllMain(PROCESS_ATTACH):
  roster.json (order,  │ compile + verify       read MRMods\Vehicles\active\roster.mrvr
  classes, labels)     │ atomic swap            verify EXE + every preimage + singleton 0x6F5ED4 == 0
                       └──> MRMods\Vehicles\active\   apply ops, map payload, publish MRVC
                              roster.mrvr             install loose-resource overlay
                              resources\ (loose)      → otherwise: stock game, log reason
                              catalog.json
```

1. **Vehicle package `.mrcar`** — the output of an SDK project build: family
   resources (`DataGx/Vehicles/<Family>/…`), physics/modification fragments,
   UI frames, audio/AI/identity metadata, stable namespace and preferred class.
   No physical ID and no native code inside; packages are portable.
2. **Vehicle Manager** keeps `MRMods\Vehicles\packages\` and `roster.json`
   (selected packages, per-class order, optional extra classes and their labels).
   "Apply" runs the existing V-CAP registry builder (plus the class layer) and
   writes a fresh `active.new\`, verifies it, then atomically renames it to
   `active\`. Reservations/tombstones keep IDs stable; a removed vehicle becomes
   a retired ID that is never reused.
3. **`roster.mrvr`** — one versioned binary: target EXE identity, RVP operations
   with preimages, the native payload (fixed private arena) and the MRVC
   descriptor. It is data for the loader, regenerated by the Manager only.
4. **Loader module "VehicleRoster" in `dinput8.dll`** — runs in `DllMain`:
   DINPUT8 is a static import of `MRallye.exe`, so `DLL_PROCESS_ATTACH` happens
   before the first game instruction, i.e. before the lazily created registry
   singleton (`0x45A3C0` / `0x6F5ED4`). This replaces the external suspended
   launcher. Only kernel32 memory/file calls are used there (loader-lock safe);
   all other modules keep their current `DirectInput8Create` boot. Any failed
   check leaves the image untouched and the game runs stock.
5. **Resource overlay** — the retail loader opens loose files before archive
   members (`0x64D530`). The module redirects relative game paths to
   `MRMods\Vehicles\active\resources\` first, so the game folder, `Data.sma` and
   original XML stay unchanged. Composed shared files (`vehicles.xml`,
   `Modifications.xml`, `VehicleSelect.xml`, UI banks) live only in the overlay.
6. **Consumers** read the published MRVC descriptor (in-process export instead
   of the launcher's environment variable): Extra Options/Randomizer AI pools,
   renderer per-car data. They never own vehicle data.

## Saves and safety

* `PlayerState.xml` stores physical IDs. **Owner decision (2026-11-11): emergency
  fallback to ID0.** If a saved selection (Quick Race, Vehicle Select, per-player
  car) references an ID that the active roster does not provide, the module maps
  it to physical ID0 at read time and logs `ROSTER_FALLBACK_ID0 key=<key> id=<n>`;
  the game must never crash on a missing vehicle. The save file is not rewritten;
  the next normal save stores ID0. The Manager still refuses to remove a vehicle
  that an active championship uses, and the competition-contract check keeps an
  active championship on its own roster.
* Menu Builder already hooks the VFS `CreateFileA` call at `0x64D573`. The resource
  overlay must chain through that same owner (one hook, ordered providers), never
  patch the site a second time.
* The private arena address (`0x10000000`, inherited from SDK33) must be free at
  `DllMain`; otherwise fail closed. Relocatable payloads are a later ABI step.
* Version policy: the module accepts only rosters built for its ABI version;
  a newer loader never reinterprets an older roster.
