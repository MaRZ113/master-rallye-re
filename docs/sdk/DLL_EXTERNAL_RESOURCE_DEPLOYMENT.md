# Compact DLL + external-resource deployment — integration boundary

Status: design/audit boundary; no new DLL deployment prototype or production claim in the first editor slice.

Existing `runtime_launcher/src/main.cpp::Launch` pins and hashes the original executable, checks adjacent wrappers, creates the game suspended, verifies the child image, optionally installs a native extension and validated patch plan, then resumes. Integrated mode passes `bundle/resource-root` as working directory; bootstrap-only uses the original executable directory. These established paths remain unchanged.

That launcher is a qualified bootstrap precedent, not evidence that an arbitrary DLL is discovered by the installed game or that a partial overlay can resolve every missing resource from the retail installation. The separate bootstrap decision, exact loader interception/fallback, dependencies/conflicts and reversible uninstall still need a bounded launch proof. No replacement of installed d3d8.dll, MRallye.exe, clean Data.sma or Randomizer is permitted.

Next implementation: select compatible builds using version-specific layout and code/data invariants, expose a small explicit bootstrap/extension interface, route one private changed vehicle resource through an isolated overlay with base fallback and a compact manifest, exercise fail/rollback/conflict paths, then prove a real original-game resource load. Hashes identify examined artifacts and plan reference builds; a matching whole-file SHA is not a universal runtime requirement. Keep the proof isolated until owner/runtime qualification. A valid fixture DX/DXT and an editor cache hit do not fulfill this deployment gate. Editor Qt package size is unrelated to the desired in-game mod footprint.

## Definitive runtime foundation — current audit

**Status: BLOCKED for installable DLL.** Read-only evidence and a reproducible plan-composition checker are implemented; no vehicle DLL, overlay, installer or game launch has been delivered in this increment.

* Retail `MRallye.exe` SHA256 `bf8aef32407eb6552c05045b8abef149f32983cedd9503b865069b444c5f96b4` is PE32/x86. Its import table includes `DINPUT8.dll!DirectInput8Create`, `d3d8.dll!Direct3DCreate8` and `KERNEL32.dll!CreateFileA` (GNU objdump, original on-disk image). An import does not establish actual loading order or that intercepting CreateFileA implements game asset lookup.
* The local rmod1 checkout has extensive uncommitted work; it was inspected without modification. Its BOOT-B source forwards the system DirectInput exports and invokes initialization once at the first DirectInput8Create. Its documentation identifies that site at `0x00570E21`, before the frontend loop, as static analysis; do not infer vehicle registry or resource initialization has not already happened. This proxy has no general SDK plugin chain. The installed game root inspected here has `d3d8.dll` but no `dinput8.dll`; that observation does not authorize occupying the slot or demonstrate coexistence with a separately installed Randomizer.
* J.2 patch metadata requires installation **before primary thread first resume**; BOOT-B runs after entry. Moving that plan to BOOT-B is not qualified. J.3 `tools/addon_collection_runtime.py` compiles the existing supported ID26/ID27 layout into the J.1/J.2 launcher contract; it is not an independent dynamic registry. Its output does not itself prove ordinary startup, fallback or new capacity.
* A current J.2 bundle has a 243-file indexed root whose `Data.sma` is a changed private archive (`131d61ee8241df9cee4885db046e4e68d4df8177df40638bab01662ee12dc736`), not clean retail (`03c2b52d451b378c7ec634132ebfab706616e33c57fea2985b83db66d3fd4b2f`). A small loose-resource overlay with retail fallback must be established against the actual engine's archive/loose-file resolution. Changing CWD alone has not proved that behavior or safe save-path ownership.
* `tools/audit_runtime_composition.py` records the candidate SHA for identification without rejecting a different hash. It verifies PE32/x86, preferred image base, file-backed RVA mappings and all declared operation preimages before comparing plans; the two plan descriptions must agree on their reference image. This is a **static plan audit**, not the version compatibility policy or a runtime installer. The examined J.2 candidate has 247 process operations plus one file-only PE-header reconstruction operation; Randomizer F3 has 17 declared operations. Two one-byte overlaps occur **inside** the F3 seven-byte Challenge instructions: VA `0x00450111` / `challenge-race-consume`, and `0x0045EC38` / `challenge-preview-identity`. Both F3 records have feature mask 1. J.2 modifies the indexed field displacement (`74`→`dc`); F3 replaces the containing instructions with branch stubs. Running installers sequentially would violate at least one expected preimage. Compare selected features and design an explicitly composed instruction/consumer path; absence of overlap for another feature mask is not proof of compatibility.

The bounded filename inventory of `D:/Game` found 43 `MRallye*.exe` files (32 distinct hashes). Retail and the different-hash `MRallye_invitation_p0.exe` both match every checked operation preimage and both have the same two plan conflicts. The other 30 distinct fingerprints hit at least one different preimage under this reference plan; this means **not yet qualified by this plan**, not inherently incompatible. Candidate-profile adaptation must validate all needed semantic invariants, not silently broaden this result. Private paths and fingerprints are recorded in ignored `definitive-runtime/exe-catalog.json`.
