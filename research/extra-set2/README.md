# EXTRA-SET2 — tyre compounds on GENERAL, PS2/PC model on Vehicle Select

Replaces the EXTRA-SET1 GEARBOX controls. Owner decisions (2026-11-09): tyres are a setup option
in every mode with a setup screen (Master Rallye, Rallye Cup, Invitation, Quick Race and any future
mode that reuses the setup screens — groundwork for a service zone); the PS2/PC model switch is a
separate row on Vehicle Select and applies immediately; GEARBOX returns to stock.

## How retail tyres really work

`RESEARCH.md` lists the addresses. The key facts:

* `Vehicles/Tyres/<surface><N>` is a database of tyre **types** N (`0x441B20` loops N until a record
  is missing, `0x441B80` builds `<surface>%d` for the five surfaces), built once (`0x4422E0`,
  singleton `0x6F5B6C`).
* Each wheel update (`0x443820` → `0x440FE0`, 4 wheels) reads the type index through
  `[[wheel+0x18]+0x14]+0x5C` and, when it changes, copies that type's five 0x30-byte surface records
  into the wheel (`+0x16C` vector, begin `+0x170`, end `+0x174`).
* AI controllers set the index to their difficulty level (`gaIContDriverLookUp` `0x42CDB0` →
  `0x42DEF0` → `0x42E0E0`, `enController_Car+0x74`, plus catch-up +1). Types 1..4 are flat AI grip
  tiers (PeakMu 0.8..2.0); PS2 types 1..10 are a difficulty × class grid. Humans stay on type 0, the
  only surface-tuned set. There are no compound tables in either version.
* The per-car string `Vehicles/<car>/Suspension/{Front,Rear}/TyreType` (`harddirt`, `Slicks`,
  `FrontTest`…) is not part of this path. EXTRA-SET1 published exactly that string, so its tyre
  choices most likely had no effect on grip (never solver-verified, see EXTRA-SET1 results).
* The retail text table keeps `TYRE TYPE` (group 7, index 8) between the GENERAL labels; the row was
  planned but never shipped.

## Compounds

Stock, Tarmac, Hard Dirt, Gravel, Grass, Mud. A compound multiplies the type-0 `PeakMu` and
`CorneringCoeff` of each surface: ×1.10 on its own surface, ×1.03 next to it, then −0.07 per step
(surface order tarmac, harddirt, gravel, grass, mud). Other fields stay exact. Values are design
defaults for owner tuning (`extra_options::grip_scale`).

The wheel hook (`0x44385B` CALL → `wheel_update`) runs the original update first, then for wheels
whose controller sub-object lies within 0x80 bytes of a human's `enController_Car`
(`Broker::Find(0x4D6FB0)("Controller/Car<n>", "ControllerCarBrokerAccess")+8`) rescales only
records that still equal a stock type-0 record (matched by PeakMu/ScaleFactor/CorneringCoeff/
gradient against `Vehicles/Tyres/<surface>0`). This is idempotent, survives a native re-copy, and
never touches AI tiers. Humans are `Race/Car<n>/PlayerType == 1` for `n < Race/NumCars`, numbered
in car order (player 1, player 2); attract mode is excluded; `Race/Type` is not consulted.
Log: `TIRE_APPLIED Car<n> … controller_offset=…` once per race, `TIRE_BINDING_PENDING` when a human
with a non-stock compound has not been matched.

## Menus

* GENERAL (`VehicleSetup3.xml`, generated by `tools/extra_set2_frontend.py`): rows move to 50 px
  spacing and a TYRE TYPE row (button 6, cloned GEARBOX multistate, native localized label 7/8) is
  added; Up/Down wraps 1…6. The car is resolved like the native setup loader `0x44D720`
  (`Frontend/InQuickRaceMode` ? `0x4ADA50`/`0x4AC660` : `0x4B0AF0`/`0x4B0630`), the player from
  `Frontend/CarSetup/PlayerID`. A change is stored at once per player and CarID; confirm on the row
  acts like confirm on the native rows (command 6 → 1). Hooks: init slot `0x690B50`, tick slot
  `0x690B4C`, command call `0x483151`.
* Vehicle Select (`VehicleSelect.xml`): MODEL row (button 3) below the carousel, Up/Down 1→2→3→1,
  car name block 25 px lower. Choices are the per-car presets from `research/extra-set1/vehicles.json`
  (SeatBuggy, Megane, Tata) or PS2/PC for every other car. Selection follows
  `Frontend/VehicleSelect/{PlayerID,CarModel}`, bumps the renderer revision and is saved at once.
  Hooks: init slot `0x690B1C`, tick slot `0x690B18`; the screen ignores command 3 natively.
* GEARBOX: no hooks, no page edit.

State: `MRallyeExtraOptions.state.ini`, sections `Car<id>` (player 1, EXTRA-SET1 compatible) and
`Player2Car<id>`, keys `Paint`, `Tire`. Toggles: `[Customization] Enabled/Tires/Liveries`.

## Renderer contract

`MRExtraVisualV2(family, participant, phase)` is unchanged in shape: phase 0 answers for the menu
car, phase 1 for race participant `n` when it is a human. The family must equal the CarID's folder
from the native registry (`0x45A3C0`, Name at `+0x24`, 0x34-byte rows), so AI cars of the same
model keep their look. V1 now means "V2 == PC bundle". The texture-transfer variant (kind 3) keeps
its exact-atlas checks. The renderer seams are still the EXTRA-SET1 private patches applied by
`stage_graphics`; they are not yet in the main renderer source.

## Verification

* `tests/rmod1/extra_native_tests.cpp` (production callbacks against a Broker/wheel harness):
  Quick Race and championship car resolution, two players, immediate commit, confirm mapping,
  human-only idempotent compound records, Stock/attract/toggle passthrough, AI untouched, generic and
  authored appearance lists, immediate revision bump, V1/V2/texture contract.
* `tests/rmod1/extra_options_tests.cpp`: compound table, record scaling, scope.
* Not verified: the controller sub-object distance on real objects, actual grip change in a race,
  menu layout on screen, PS2/PC switching for cars without an authored preset. These are the owner
  test.
