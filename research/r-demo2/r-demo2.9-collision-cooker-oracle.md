## Tag101 base/reference points and base scalar

The parsed tag101 base geometry point and Rep-A `geometry_b` point are byte-identical in each file. Their coordinates are within `3.95e-8` of the Rep-B AABB center in this pair. They shift by +0.10 X along with the hull. This is an observed equality for this controlled pair; no field renaming follows from it.

Rep-B `geometry_b` is `(-0.046282746, 0.764021754, -0.394585639)` at baseline and `(0.053717259, 0.764021754, -0.394585639)` in the candidate. Its semantics remain unresolved.

The tag101 base scalar is `2.6045312881469727`, bytes `a4b02640`, in both files. It is bit-identical under the translation. This establishes translation invariance in the controlled oracle, not radius semantics by itself. Existing four-vehicle corpus analysis and this recomputation show the scalar equals float32 rounding of the maximum distance from the tag101 base point to a Rep-A AABB corner in each tested baseline: Trooper, Jump, NewRav and Tata. Thus the radius-like relation is **CORPUS_SUPPORTED** for those inputs; no wider class claim is made.

## Marker-1339 formulas

Each formula was recomputed independently for baseline and candidate from `render positions ∪ Rep-B geometry-A vertices`.

| Hypothesis | Baseline maximum component error | Candidate maximum component error |
|---|---:|---:|
| A. Stored min/max equal union AABB | min `0`; max `1.19209e-7` | min `0`; max `1.19209e-7` |
| B. Center equals float32 `(min+max)/2` | `5.96046e-8` | `5.96046e-8` |
| C. Radius equals float32 max distance from center to union points | `2.38419e-7` (one float32 ULP) | `2.38419e-7` (one float32 ULP) |

The raw nearest-float32 radius is one ULP above the stored Trooper radius in both files. The existing safe enclosing-bounds policy also differs from stored by one ULP. Three additional 9.3.1 corpus-shipped controls (Jump, NewRav, Tata) reproduce min/max and center exactly; their stored radii equal nearest float32 rounding exactly. This makes the render-plus-Rep-B point set **CONFIRMED_BY_CONTROLLED_ORACLE** for Trooper and **CORPUS_SUPPORTED** across the four checked same-build assets. Exact radius rounding order remains an implementation detail to preserve as a one-ULP uncertainty.

The X-boundary switch is direct differential evidence for both point sets: baseline positive X max is render-dominated (`render 1.02218807 > Rep B 0.94192177`); candidate positive X is Rep-B-dominated (`Rep B 1.04192173 > render 1.02218807`). Negative X remains render-dominated (`-1.02218807` vs baseline Rep B `-0.94192147`, candidate Rep B `-0.84192145`).

## R4G impact

The existing R4G `compute_bounds1339` point-set policy is now supported by the controlled source-only collision translation and three additional same-build corpus controls. Its outward radius rounding is conservative and can differ from native stored values by one float32 ULP. This strengthens bounds recomputation as an implementable R4G policy; it does not require byte identity. Production code remains unchanged in this phase. Secondary descriptor changes remain excluded from automatic rewrites.

## Runtime/cooker history and remaining uncertainty

The prior 8.4.1 +0.4-X collision edit crashed at stock `PlaneThickness ~= 0.0005000000237487257`; the same source edit with `PlaneThickness = 0.00052` completed hull building, continued loading and visibly changed collision. That causal result closes the old immediate NULL-crash pursuit for now. It does not transfer a plane threshold to 9.3.1.

The available native-style plane replay pins the 8.4.1 source/EXE and is **NOT_RUN_UNSUPPORTED_FOR_9_3_1**. No 9.3.1 complete plane-decision signature is claimed. The internal native algorithm beyond observed outputs, secondary descriptor production, exact face-scalar rounding and auxiliary geometry roles remain unresolved.
