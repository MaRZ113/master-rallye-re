## R-DEMO2.3 serialized hierarchy and runtime-input boundary

The exact read-only 9.3.1 Trooper car.gxm is 222,754 bytes, SHA256 5caed6da1213f17e2638d0ee47860cf521d4715475418e028bfd13f7c0e87642. The conservative GXM prefix parser places the final opaque tail at 0x36346 (732 bytes). That tail contains length-prefixed Model and mesh-name strings in the same order as the matching car.txt sidecar, ending with $chull(Trooper) at EOF.

The hierarchy tail preserves an ordered mesh-span correspondence: the trailing u32 pair in each nonterminal name record matches the next sidecar mesh Index and Size. For example, the bytes following Model match sidecar shell (0,98), bytes following shell match frontgrill (98,8), and bytes following blight $perspex match $chull(Trooper) (1911,68). The final $chull(Trooper) name has no trailing fields. An offline audit matched all 29 names (Model plus 28 meshes) and all 28 spans to the matching 9.3.1 sidecar. This is CONFIRMED_BY_BYTES against that sidecar; it does not establish the meaning of the preceding control bytes or the runtime parent/child links.

Each name record includes 01 01 control bytes; intermediate records also contain a u16 and two u32 values. Do not label the u16 as a child count: its value after shell is zero while the sidecar shows two nested meshes under shell. The GXM tail therefore establishes name order and a shifted mesh-span association, but not a proven serialized hierarchy tree.

On the exact 9.3.1 executable, static decompilation further shows:

- FUN_005de630 searches node names for $chull, uses FUN_005dea80 to descend through loaded nodes, counts mesh inputs with FUN_005df060, then allocates and fills hull input before later hull-processing calls.
- FUN_005df370 appends each selected node's triangle corner positions and walks child heads via object +4, then sibling links via +8. It recurses through the selected node's descendant mesh lists. The mesh's internal triangle range/count are read through the virtual mesh accessor (+0x1c / +0x20 in that returned record); three C-position indices are read at +0x1c, +0x20, and +0x24 within each 0x34-byte internal record. The position-buffer pointer is obtained from the loaded object at +0x38.

Those are post-loader runtime offsets. No loader function/field mapping yet connects the serialized tail's control bytes and span pair to the loaded node's +4/+8 links, or proves that sidecar range [1911,1979) covers every triangle the runtime recursion emits. Thus the controlled offline translation's 36 referenced C ids remains a flat-range result, not proof of complete recursive builder input coverage.
