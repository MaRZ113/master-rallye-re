# Force one specific player vehicle

## Verdict

**Status:** feasible with localized patches. **Confidence:** medium for a
prepared Quick Race selection; low-medium for cross-mode overrides. The
earliest verified Quick Race player identity source is the active player's
stored absolute physical ID returned by `FUN_004ADFB0` at `0x004ADFB0`. The
Quick Race setup owner `FUN_0047B780` reads it, publishes `Race/Car0/CarID`,
then resolves class from the selected VehicleRecord and publishes
`Race/Car0/CarClass`. Vehicle Select initialization at `FUN_00480B60` restores
the active player's physical ID through the sparse physical-ID/class-local
mapping. These are related but separate native boundaries.

An override must choose one ID before the lobby is displayed, then use that
same ID for the Vehicle Select highlight, model preview, manufacturer/model
text, Quick Race summary, and eventual `Race/Car0`. `CarClass` must be derived
from that same registered physical record. Do not change PlayerID, PlayerType,
controller ownership, or DriverID. Do not draw again when Start is pressed.

Challenge has an authored player/opponent pair and a prepared opponent cache
that synchronizes preview with the race. A forced player ID there is only
acceptable if the event's authored identity checks, opponent pairing,
success conditions, retry and preview all consistently accept the override.
No present evidence proves arbitrary cross-class overrides in Challenge,
Invitation, Cup or Master Rallye.

## Precedence and active events

The proposed order is `ForcedPlayerCar > Player.Randomizer > native selection`
only when the selected mode explicitly supports the override and the ID is
registered/materializable. If a mode rejects it, show a diagnostic and use
the native path before any preview is published. Do not silently display one
car and race another. A newly generated Cup/Master competition may freeze one
choice if its rules allow it; an existing Cup or saved Master Rallye roster
must not be rewritten. Retry reuses the prepared car; a new event boundary may
prepare again.

Cross-class vehicles can materialize, but that alone does not establish
competition validity. T1 in a T3 competition may alter class-specific
standings, unlock flow, AI pool selection, or event objectives. First qualify
same-class forcing in Quick Race. Consider cross-class Quick Race as a
separate policy after the rules-title and AI-class inputs are traced.

**Required native hooks:** prepared selection at the Vehicle Select/lobby
boundary and a narrow Quick Race player-ID read override before
`0x0047B780` publishes Car0. The frontend writers must share the prepared
physical ID. A mode-specific authored-event path is required for Challenge.
All changes must be generated by the existing unified native patch owner and
must preserve original instructions/ABI when disabled.

**Unknowns:** exact confirm/commit ordering in every mode; saved campaign
player identity; class constraints and effects on event scoring; split-screen
independent choices; failure UX when an addon is inactive.

**Risks:** lobby/race mismatch, stale class, save incompatibility, active
competition mutation, or an event that depends on authored player identity.

**Minimal PoC:** fixed same-class stock CarID in Quick Race; verify highlight,
name/model, preview, Car0 physical ID/class/family, race, Restart and return.
Then test one campaign only at new-event creation. **Effort:** medium for
Quick Race; high for Challenge and campaign modes.
