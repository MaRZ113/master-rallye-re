# Deterministic offline compilation

`tools/mrtool.py addon` provides `validate`, `build`, `verify`, `inspect`, and
`check-frontend-state` commands. Inputs are UTF-8 JSON; duplicate object keys,
unknown fields, unsafe paths, unsupported capabilities, and conflicting IDs or
resource families are rejected.

The resolver first reserves explicit IDs, then allocates `auto` IDs in stable
`addon_id` order from the selected capability profile. Class-local indices are
generated by appending each addon to its declared class. Both forward and
reverse maps are emitted. The registry layout is computed from the maximum
resolved physical ID and target profile constants:

```text
record_count       = highest_physical_id + 1
RaceTest_base      = header_bytes + record_count * vehicle_record_stride
allocation_size    = RaceTest_base + RaceTest_count * RaceTest_stride
```

For the two examples this produces 28 records, RaceTest base `0x5B4`, and
allocation size `0xC68`. This reproduces the audited I.0 formula. It is a
planner result, not a new executable patch.

Build outputs are canonical sorted-key JSON: `addon-plan.json`,
`frontend-overlay.plan.json`, `resource-inventory.json`, and a hash manifest.
The frontend artifact is explicitly semantic planning data, not native XML.
Identical manifests and capability files produce identical logical outputs.
The verifier checks the exact output file set, every SHA256, and the offline-
only boundary. Existing destinations are refused rather than overwritten.

If `--assets-root` is supplied, the compiler requires each referenced vehicle
folder, verifies `car.dx`, `complete.dx`, `wheel.dx` through the existing DX
parser and dependency resolver, resolves every referenced DXT, validates DXT
headers/sizes, hashes each staged runtime file, and copies only the required
model and resolved texture resources. The existing vehicle-project and
collision validators remain the authoring checks; the addon compiler does not
re-author or repair payloads. Shared DataGame physics/modification records are
described in the semantic plan and are not synthesized into a native overlay
in J0.

The current capability profile is
[`retail-2001.json`](capabilities/retail-2001.json). It pins retail SHA256
`bf8aef32407eb6552c05045b8abef149f32983cedd9503b865069b444c5f96b4` and
runtime-qualified addon IDs 26/27. A different executable must use a separately
audited capability profile; the compiler never infers compatibility from a
similar file size or version string.

## Donor project build (J.3-A)

`addon init --name ... --class T1|T2 --donor ... --output ...` creates a
metadata/source scaffold and does not copy donor assets. `addon project-validate`
joins the addon manifest checks to the existing VehicleProject DX/DXT,
dependency, bounds and collision checks. `addon project-build` emits the
offline compiler plan plus validated assets under the new model family.

With both `--retail-data-sma` and `--retail-data-root`, the project build also
requires the exact Data.sma hash/size in the target capability profile and
byte-compares unpacked `DataGame/vehicles.xml` and `Modifications.xml` to the
archive members. It appends verified donor-value clones under the independent
physics family, preserving stock bytes. The generated DataGame rows are
included and hashed in `resource-inventory.json`.

This adds resource generation only. It does not change the J.0 semantic frontend
artifact into native XML or make a runtime-installable package. The exact
native reference bundle remains profile-bound to Mercedes + R5VQualifier. See
the J.3 [quick start](j3/quick-start.md) and [release boundary](j3/release-boundary.md).
