# R-MOD1-D native integration plan

## Provenance and status

The candidate plan is generated by `tools/r_mod1_native_plan.py` from the
exact supported pristine retail image and the built runtime-core DLL. It does
not consume a research-patched EXE. The generated package plan is
`STATICALLY_VERIFIED_RUNTIME_PLAN_TEMPLATE`; it is not a runtime qualification.

Retail identity: I386 / PE32, SHA256
`bf8aef32407eb6552c05045b8abef149f32983cedd9503b865069b444c5f96b4`,
3,121,214 bytes, preferred base `0x00400000`, image size `0x00311000`,
relocations stripped, OEP RVA `0x001C4602`.

## Image operations

All target addresses below are RVAs; the launcher resolves them against the
verified mapped main-module base. Replacement lengths equal original lengths.
Every listed preimage is checked before the first process-memory write.

| Operation | RVA | Expected bytes | Owner / activation |
|---|---:|---|---|
| `oep-bootstrap` | `0x001C4602` | `55 8B EC 6A FF` | Shared bootstrap; installed whenever either feature is active. |
| `quickrace-selector-init` | `0x0005810B` | `8B 84 24 8C 00 00 00` | R-AI1.2 class selector; Randomizer only. |
| `quickrace-selector-loop` | `0x00058379` | `8D 4C 24 30 E8 1E 93 FB FF` | R-AI1.2 class selector; Randomizer only. |
| `quickrace-selector-end` | `0x000582D5` | `8A 94 24 94 00 00 00` | R-AI1.2 class selector; Randomizer only. |
| `opponent-list-append` | `0x00079DCB` | `8B 54 24 14 89 74 24 28` | One..Seven localized list construction; Extender only. |
| `opponent-arrow-bound` | `0x0007A32C` | `83 FD 02` | Native upper index; generated replacement is materialized as 1..6 from configured maximum. |
| `quickrace-start-guard` | `0x0007AD0C` | `E8 6F 0A 00 00` | Quick Race pre-start capability check; on allow, calls native setup exactly once and continues to `0x0047AD11`; Extender only. |

The race-scene getter call at VA `0x0040869B` / RVA `0x0000869B` is not a
patch operation. Its exact retail bytes `E8 C0 E0 0C 00` remain in place. The
target getter reads its output pointer at `[ESP+4]` and returns with `RET 4`.
A wrapper that CALLs the getter inserts its own return address into that
argument slot; v10 crashed at `0x004D684E` while writing through the bad
pointer. See [`v11-observer-hotfix.md`](v11-observer-hotfix.md).

The selector class choices leave physical CarID selection and DriverID selection
to their native owners. The start gate is bound to the Quick Race callback
callsite, not a global race initializer. Its denial path replays the observed
parent epilogue (`POP ESI; ADD ESP,0x30; RET 4`) without making the screen
transition. Its allow path calls the original setup exactly once and branches
to the original continuation at `0x0047AD11`, which requests frontend
transition state 10 via `0x0045D910`. It does not inspect Race counters before
this transition.

## Remote templates and startup ABI

The plan reserves two aligned, non-overlapping x86 regions:

| Region | Base | Allocation | Final protection | Used template bytes |
|---|---:|---:|---|---:|
| code | `0x70000000` | `0x10000` | `PAGE_EXECUTE_READ` | 6,676 |
| data | `0x70010000` | `0x10000` | `PAGE_READWRITE` | 8,930 |

The fixed ranges are conditional: the launcher requires `MEM_FREE` across the
whole allocations. If unavailable, it aborts rather than selecting a new,
unaudited address. Template SHA256 values are embedded in the generated native
header and public plan. The data template contains the UTF-16 DLL path, bounded
INI blob, export names and function slots; the path is capped to avoid overlap.

The OEP bootstrap preserves flags and general registers, resolves
`LoadLibraryW` using the retail imported `LoadLibraryA` and `GetProcAddress`
IAT cells, loads the absolute adjacent runtime DLL path, resolves five exact
versioned exports, configures the shared core, restores state, replays the
five displaced retail OEP bytes and jumps to the original continuation. Any
resolve/configuration failure calls the imported `ExitProcess` with a distinct
failure code. This happens at the verified process entry point before retail
CRT/game constructors; actual runtime sequencing remains untested.

The x86 DLL uses a no-work `DllMain`; its CRT finishes as part of the normal
`LoadLibraryW` call. Export functions use a fixed C ABI and translate failures
to fail-closed return values. The launcher and DLL are statically linked to
the MSVC runtime (`/MT`) and carry no Python/runtime dependency.

## Launcher installation protocol

The x64 launcher verifies the retail path, exact size/hash, PE32/I386 layout,
runtime DLL hash/architecture/exports and configuration before process
creation. It pins the executable and DLL handles to prevent replacement and
rechecks the contents. It creates the original EXE with
`CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT`, checks full child image path,
x86 process architecture and the audited PE image mapping without consulting
the loader's module list. The retail PE is I386/PE32, has relocations stripped,
and is pinned at `0x00400000` with `SizeOfImage=0x00311000`. The launcher walks
that exact extent with `VirtualQueryEx`; every covered region must be
`MEM_IMAGE`, `MEM_COMMIT`, and have `AllocationBase=0x00400000`. It then checks
readable mapped PE headers and byte-compares every complete executable section
with the pinned file. It verifies every selected image preimage, page
mapping/protection, operation overlap, fixed allocation availability and
branch layout before writing.

It writes/readbacks code and data, changes code to RX, then installs each
selected image operation under temporary page-write permission and restores
the original executable page protection. It flushes instruction caches and
resumes only after all operations read back exactly. Any pre-resume failure
terminates the still-suspended process; it is never resumed with partial
installation. On exit it hashes the still-pinned on-disk EXE and confirms the
retail SHA is unchanged. No on-disk game file is a patch target.

This ordering is implemented and exercised by build/verification tests. The
v10 `--preflight` path creates the original process suspended, performs the
mapping checks above without writing memory, and terminates the child before
any resume. Synthetic tests cover absent/misplaced mappings, allocation
type/state, changed headers and changed executable sections. The real v10
Windows suspended-process preflight passed before native writes. This proves
the mapped pristine-image checks on this host; it does not prove the modded
game was resumed, renderer-proxy compatibility or gameplay.

## Candidate scope and exact limits

- Quick Race mode ID2 only for participant-count integration. V12 statically
  admits one human plus four through seven AI under the experimental/count
  gate; only four AI / five total is currently human-runtime-confirmed.
- Native 1–3 AI path is retained.
- UI can show the configured maximum up to seven AI.
- Four through seven AI require explicit experimental opt-in, a configured
  maximum at least as large as the selection, and one-human Quick Race
  topology; the raw frontend SplitScreen flag is diagnostic only before Race
  participants exist. Actual one-human qualification uses Race/NumPlayers and
  participant PlayerType after setup. No post-setup veto or observer is
  installed. The precheck calls native setup once and continues the original
  state-10 transition. Use Observatory or an independently audited debugger
  point for race-state evidence.
- Native count readers, chooser caller sites, and the CarID/DriverID/refill
  body of `FUN_00458090` remain unchanged. The Randomizer installs only three
  existing class-policy seam hooks. Its exact-build static loop is count-driven
  and its physical-ID pool refills after unique candidates are consumed. Candidate tests use `Duplicates=WhenNeeded`; a
  repeated-ID full race and 5–7 AI results/lifecycle remain human gates.
- Track10 / Italy_S4, human ID0/T1 and Ghost OFF are recommended first-test
  conditions inherited from the prior five-car qualification. They are not
  universal Start guards. Other track/car combinations remain unqualified.
- Repeated-ID seven-AI lifecycle is not in this candidate.
- Cup, Master Rallye, Invitation and Challenge native ownership is unchanged.
- No addon or Vehicle SDK runtime is loaded.
- `dinput8.dll` is neither built nor included; existing `d3d8.dll` is never
  replaced or modified.

See the generated `native-patch-plan.json` and candidate manifest for exact
runtime-core, template, operation and package hashes. See
[`runtime-handoff.md`](runtime-handoff.md) for the bounded human test sequence.
