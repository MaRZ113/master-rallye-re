# Global HUD Hide — implementation and evidence

Status: **GLOBAL_HUD_HIDE_READY_FOR_RUNTIME**. The candidate is built and the static/native policy tests pass. A human gameplay run has not yet been performed.

## Exact native boundary

The target was verified as the pristine retail `MRallye.exe`, SHA256 `bf8aef32407eb6552c05045b8abef149f32983cedd9503b865069b444c5f96b4`, size 3,121,214 bytes, PE32/I386, ImageBase `0x00400000`.

REA 6.4.0 was run against that exact image with its Ghidra provider, Ghidra 12.1.4. The provider reported an x86 PE executable and an ephemeral, source-immutable analysis session. Its function dossier for `0x0056D110` (`FUN_0056d110`) reports the complete body `0x0056D110–0x0056DB0F` (2,560 bytes). The decompiler reads the packet pointer from `entity+0x4c`, checks packet flags/mode, and submits FVF `0x142` before the native packet draw. Ghidra's bounded incoming-reference query returned `0x0056BAE1` and `0x0056CE0A`; that operation does not label edge kinds, so the addresses are retained as references rather than promoted to caller semantics. Existing A3h evidence and the production callsite verifier identify the final `DrawPrimitive` return site as VA `0x0056D7C4`, RVA `0x0016D7C4`.

That consumer is shared by HUD and frontend packet rendering. A 2D FVF, triangle topology, or callsite alone therefore cannot authorize hiding. Existing renderer work already owns the exact-retail consumer hook and current packet identity check; this feature adds no second UI hook. At each candidate draw, the new gate also re-reads the live native race/UI context rather than trusting a prior frame snapshot.

The normal race/replay proof requires the exact retail image, intact observer/UI hooks, render thread, current D3D scene/device, current consumer identity, committed `Hud/Hud0`, a correlated successful `RaceTest/<course>` root and exact `DataScene/Hud/Hud0.xml` child, exactly one local participant, and a readable typed pause boolean. HUD-only admission allows fully read participant phases 0/2 and native startup phase 1 only while the live SceneManager countdown is positive; that state is surfaced as `gameplay_start_countdown`. The camera/freecam and race-write certificates retain their original stricter participant-state gate. Typed `Race/PlaybackReplay=1` remains a HUD-only exception when network sync, attract mode, ghost playback, network players, and unsupported race settings are clear.

Attract Demo uses a separate, strict route: the committed scene must be `Hud/AttractMode`, its successfully committed child job must belong to the proven track root, and typed fields must report Race Type 14, zero players/network activity, `AttractMode=1`, no ghost/replay/finish flags, and a participant count matching the live readable owner. This route preserves the root owner proof across the exact Attract child request but does not require the absent `Race/PauseMenu/Enabled` entry. It still requires the exact native packet consumer, current render/device and packet identity, FVF `0x142`, triangle list, and positive primitive count. Ordinary frontend scenes, unknown children, bad ancestry, stale owner data, and uncertain states remain fail-open.

This confines hiding to the verified race packet stream in gameplay and active replay. Frontend, loading, results, unsupported builds, and stale scene snapshots fail open. In a certified replay pause, the separate policy hides every complete, current draw identity at the exact native UI packet consumer. This covers both the learned race HUD and the additional packets that appear with the replay pause window. Incomplete or stale draw identity still fails open. For an ordinary gameplay pause, `PreservePause=1` hides only race HUD packet identities learned while driving and retains newly appearing pause-window UI; `PreservePause=0` hides every complete, verified UI packet at this same consumer. A paused Freecam always hides complete verified pause UI whenever global HUD hiding is requested, independent of `PreservePause` and the optional Clean View pilot switch. That branch requires the existing strict fresh race/camera/device/UI context proof.

## One preference and one H edge

`Device8::hud_visibility` owns the session preference. The proxy polls the configured virtual key once at `Present`, only while the game HWND is foreground and not minimized; it observes the high key-state bit without consuming input. Focus loss resets the edge detector. The request survives camera changes, Freecam changes, pause, scene transitions, and device Reset. It starts visible by default.

`[FreeCameraKeys] ToggleCleanView` is now a legacy alias for `[HUD] ToggleKey`; it has no second toggle handler. `GameFov` receives the same preference, while the established Clean View admission still decides whether the pause overlay can be suppressed. The stock `DataGame/options.xml` does not bind DirectInput scan code `DIK_H` (`0x23`, decimal 35) to either keyboard layout. The default H binding therefore does not collide with pristine controls. Native input remains untouched; if a user rebinds a game control to H, the proxy key can be changed in the INI.

The production Win32 INI reader reads `ToggleEnabled`, `ToggleKey`, `HiddenAtStartup`, `PreserveMenus`, and `PreservePause`. `PreserveMenus=0` is forced to true. `PreservePause=1` is the default and affects only the ordinary-camera gameplay pause; set it to `0` to hide its complete verified UI. Replay pause and verified paused Freecam behavior do not follow this option. Existing configurations without a `[HUD]` section keep H through the old `ToggleCleanView=H` alias. Legacy `CleanViewEnabled=1` maps to `HiddenAtStartup=1` only when the new key is absent.

F10 frame metadata contains `hud_hide` with requested/effective state, policy readiness/reason, current context (`gameplay_running`, `gameplay_start_countdown`, `attract_demo`, `replay_running`, or a preserved paused/unknown context), replay/Attract/countdown flags, exact-build/device/hook status, verified and suppressed draw counts, and ambiguous rejections. Race lifecycle records also include the captured native request origin for each job. `effective_hidden` means at least one draw was actually suppressed in the captured frame; it does not merely mean H was accepted. Menu draw count remains `null` because the shared consumer does not expose an independently proven menu category.

## HUD suppression cost

Review of the 13 October captures found that `global_hud_request_` mirrors the H preference into `GameFov::clean_view_requested()`. The UI draw wrapper treated that request as a reason to bypass its per-frame context cache, calling `live_race_hud_context()` for every UI primitive while HUD hiding was active. That routine takes the race-observer lock and performs multiple native/Broker reads, so the repeated synchronous work was on the render thread and scaled with UI draw count. The wrapper now refreshes this context at most once per D3D frame; subsequent UI draws reuse the snapshot. Clean View's independent strict camera/device/UI admission remains evaluated at each draw. Unit tests cover the frame-scoped sampling contract. A post-fix gameplay capture is still needed to measure the visible improvement on the user's machine.

## 12 October Freecam and paused-HUD diagnosis

The fresh session `session-20261012-064013-17824.jsonl` recorded an enabled Freecam request with `AllowUnpaused=1`, but its FOV values were outside the parser's supported lens range: `CinematicVerticalFOVDegrees=10`, `MinVerticalFOVDegrees=10`, and `MaxVerticalFOVDegrees=120`. The old parser folded those optional lens checks into the global Freecam validity bit, so `flight_config.enabled` became false and no Freecam input/state records were created. This also prevented the paused Freecam Clean View path from being available.

The paused frame `frame-22816-d1-00004842.jsonl` confirms that H itself was accepted: `requested_hidden=true`. It also reports `effective_hidden=false`, `clean_view_suppressed_draws=0`, and `policy_reason=interactive_pause_preserved`. This correctly preserved the ordinary interactive pause menu; the camera's invalid config meant H could not reach the independent paused-Freecam Clean View gate.

The fix isolates an invalid optional lens from Freecam activation and clamps a nonzero configured target to valid bounds. The active `MRRRenderer.ini` used `CinematicVerticalFOVDegrees=30`, `MinVerticalFOVDegrees=30`, and `MaxVerticalFOVDegrees=110`; the session capture showed a stock lens of 75 degrees transitioning toward the configured 30-degree target on every Freecam activation. `InheritStockFOVOnToggle=1` now defaults to preserving the effective native/gameplay lens at entry and after re-entry. Set it to 0 to retain the old configured-target behavior. Z/X still adjust within the configured minimum and maximum. Invalid bounds disable only the optional cinematic lens and are reported through `free_camera_config`. The prior INI contents are preserved in the adjacent `.before-freecam-fix-20261012` backup. Normal pause learns race HUD identities while driving. `PreservePause=1` hides those known HUD draws and leaves pause-only packets visible; `PreservePause=0` hides all complete verified draws in the ordinary gameplay pause. A paused Freecam hides all complete verified UI under the same strict current-context admission regardless of either setting or `CleanViewPilot`. Replay pause retains its existing separate policy.

## Paused replay HUD fix

The fresh frames `frame-16944-d1-00017252.jsonl` and `frame-16944-d1-00006809.jsonl` belong to the same replay owner (`race_generation=11`, `owner_lifetime=2`) and UI epoch 4. The running frame contains 274 exact UI-consumer draw records across 33 complete native packet identities. The paused frame contains 482 records across 37 identities. All 33 running identities recur while paused; pause adds four identities (208 records). Neither capture has identity overflow or unmapped draws. The previous policy rejected every paused global-HUD draw as `interactive_pause_preserved`, so none of the already-proven replay HUD packets were hidden.

The first implementation learned full packet identities during certified running replay and hid only those identities after pausing. The fresh same-session captures now isolate the remaining defect: with the typed `Race/PauseMenu/Enabled` value false, the UI probe recorded 32 identities; with replay enabled and that value true, it recorded 35 identities. Three additional complete identities remained forwarded (24, 180, and 2 native draws respectively), matching the visible pause window. An earlier paused capture showed the same pattern with four pause-only identities. The base HUD identities were suppressed, so the remaining window was not a failed H toggle or stale replay context; it was the old fail-open rule for new pause-only identities.

The corrected replay-pause rule requires the same strict exact-build, render-thread, device, current scene/owner, typed replay and pause state, exact native UI callsite, consumer scope, FVF `0x142`, triangle-list topology, positive primitive count, and complete current packet identity. Under that conjunction it suppresses all verified UI draws, including pause-only identities. It still preserves ordinary race pause menus, frontend/loading/results, incomplete identities, stale contexts, and unsupported builds. The learned running-replay signature registry remains useful provenance and reports which paused draws were known HUD versus new pause-overlay UI. Human visual confirmation of the rebuilt candidate remains required.

When the global HUD policy suppresses verified paused-Freecam UI, the F10 summary identifies `policy_reason=paused_freecam_global_hud_suppressed`; a normal camera pause with `PreservePause=1` reports known race HUD suppression or unknown pause UI preservation; the opt-in `PreservePause=0` route reports `paused_race_full_ui_suppressed_by_config`; replay pause reports `paused_replay_ui_suppressed`. These code and config changes still require the human runtime retest in [runtime-handoff.md](../live-freecam/runtime-handoff.md).
