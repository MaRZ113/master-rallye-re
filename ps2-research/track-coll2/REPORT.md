# W1: full PS2 collision for every course

Part of the full PS2 course conversion (plan in `../TRACK_RESEARCH_INDEX.md`, owner's decision: PS2 behaviour at the course borders, including the
solid exterior shell and the void areas). Offline work only; nothing has been run in the game.

## Result
`build_collision.py --course <name>` writes a loose course DX: the retail render section unchanged plus a new tag100-starting suffix
built from PS2 data:
- **tag100 tree:** the whole PS2 `.BSP` converted (`ps2_to_tag100.py`).
- **tag1339:** retail (render bounds; the render is unchanged in W1).
- **tag1400:** built from the PS2 landscape triangles (`surface_grid.py`); `--surface retail` keeps the retail block instead.
- **tag1500:** retail (the sector table of the render batches, see `../track-render1/NOTES.md`).

`run_all.py` (or `../course-port/build_course.py --all`) builds and checks all 36 courses (`collision-36.json`). The PS2 BSP and the converted
tree agree everywhere the checks look: seeded random points in the course box, vertical first-contact columns over the PS2 landscape (the PS2
shell included), horizontal rays at car height and the engine's nearest-plane fallback (section on invisible walls). The table at the end is generated by `summarize.py`.

## How the tree is converted
The PS2 tree and the PC tree are the same BSP family (T2-BSP-FORMAT.md): a plane node has a back link (child, n.p + d < 0) and a front link (sibling);
leaves are solid or empty. PS2 adds payload leaves, convex solids: a point is solid when n.p + d <= -1e-4 for every plane of the leaf's run.
The converter rebuilds the PS2 tree node by node with the existing `tag100_tree` structures:
- plane node -> plane node with the same float32 plane;
- solid / empty leaf -> solid / empty leaf;
- payload leaf -> chain of its run planes (front: empty leaf, back: next plane, last: solid leaf). Each run plane is moved by the PS2 epsilon,
  rounded up to the next float32, so the PC back side stays inside the PS2 solid. Without this, thin cells kept a 0.0002-unit solid sheet that the
  PS2 test does not have (found on Italy2/Italy3 by the column check).

Remaining exact limit: a float32 step at |d| ~ 2000 is 2.4e-4, so a moved plane can sit up to one step further inside than PS2. The PS2 solid is
then up to 2.4e-4 thinner, never thicker. On SpainS1 and its flip one column of 18,035 runs within 3e-5 of a vertical wall plane and lands on the
other side of it; that is the one differing column in the table.

The walk carries each node's convex cell. A plane is dropped only when every vertex of the cell is on one side of it. An earlier version decided by
the volume of the clipped parts and dropped real but thin pieces.

## Plane codes (geometry and physical properties are separate)
The engine skips a plane whose code is negative as int32 (no contact on it). PS2 tree planes coded 0xFFFFFFFF keep that code (`ps2_splitter`, see
the next section); every other new plane gets a non-negative code. What the code means beyond that is not known; R5T-F.2.1 found it equals the
ordinal of a source collision triangle.
- **Choice:**
  0. PS2 tree plane with code 0xFFFFFFFF: 0xFFFFFFFF (`ps2_splitter`, 3,064 planes on Turkey2);
  1. the code of a retail PC plane with the same equation (`pc_same_plane`, 82 percent on Turkey3);
  2. else the ground code on the retail descent path at a point of the plane (`pc_ground_path`);
  3. else a course default. Provenance is counted per course.
- **What this proves.** A valid code means contact is possible, nothing more. At the first-contact plane of every checked column the converted
  code equals the retail code on 96 percent of Turkey3 columns where both surfaces are at the same height. The remainder are PC triangles the PS2
  data replaces. If the engine reads physical properties through this code, those columns get the property of the nearest PC ground.

## Invisible one-sided walls (owner's game test, Turkey2, 2026-10-19)
**Report.** On Turkey2, early in the race, the car's left side was stopped by an invisible wall next to a wooden fence along a grassy field; the
wall stopped the car from one side only. PS2 has no wall there.

**Not a geometry error.** The converted tree has the same solid and empty space as the PS2 BSP: 0 differences on random points, vertical columns
and (new check) 20,744 horizontal rays at car height on Turkey2. The wall is in the choice of the contact plane, which depends on plane codes.

**How the engine chooses the contact plane** (MRallye.exe, Ghidra; the PS2 functions are the same, SLES_509.06):
1. The contact generator `0x6363C0` calls `0x636770`. That traces 1 unit from the contact point backwards along the relative velocity, then forwards
   (`0x6369B0` -> `0x62F840`; PS2 `0x243718`). It takes the nearest crossing whose plane code is not negative, and only if the trace leaves the
   solid from the back to the front of that plane.
2. If neither trace finds such a plane, it uses the nearest-plane fallback `0x62F5F0` -> `0x61FFF0` (PS2 `0x2433F8` -> `0x237610`). It walks the
   descent path of the point. At each plane node with the point on or behind the plane, the node plane becomes the contact plane when its code is not
   negative and |n.p + d| is the smallest so far. The PS2 payload leaf (`0x2365E0`) adds its run planes the same way, while the best code so far is
   not negative. Start values: distance FLT_MAX, code 0xFFFFFFFF (PC static data written at `0x4E67D0`).
3. For a wheel or hull point slightly under flat ground with a mostly horizontal velocity, the 1-unit horizontal trace stays under the surface, so
   the fallback (2) decides the contact plane. That is the common case when driving.

**Cause.** PS2 tree planes coded 0xFFFFFFFF are splitters: in the PS2 game the fallback never takes them. The converter gave every plane a
valid code, so under the ground a vertical PS2 splitter closer to the point than the ground surface became the contact plane. The push then goes
along the splitter normal, sideways. A car moving towards the back side of the splitter is pushed back. A car moving the other way is pushed
forward and passes. That is an invisible wall that works from one side only. It appears in a narrow band (the penetration depth) along every
splitter that crosses the ground.

**Evidence (offline).** `validate_collision.ps2_fallback` / `pc_fallback` transcribe the fallback for both trees. They are checked for a point
0.005 to 0.3 below the PS2 contact of each validation column:
- Turkey2, package before the fix: 81 of 20,744 points get a steep plane (|ny| < 0.5) on PC where PS2 gets a non-steep one. In a test sample,
  26 of the 32 differing points chose a PS2 splitter coded 0xFFFFFFFF; the other 6 were near-identical ground planes.
- After the fix: 0 steep-on-PC-only points. 13 points (0.06 percent) still choose another plane:
  - 10 are near-identical ground planes (a pruned or inset run plane);
  - 3 are points where PS2 finds no plane at all, because the payload leaf accepts its run planes only after a valid tree plane.
  None is a wall.
- Near SplitTime0 (x 450..850, z 180..580, 1-unit grid, point 0.05 under the PS2 surface, open ground only) the old tree had 98 such cells,
  including two lines along the road beside the fenced field (x 588..614, z 340..402, within 1.5 units of the RaceLine). The fixed tree agrees
  with PS2 in all 98.

**Fix.** `ps2_to_tag100.convert` keeps 0xFFFFFFFF on PS2 splitter planes (`keep_splitters=True`, the default; `False` rebuilds the earlier
behaviour for comparison). Geometry is unchanged. The package check `no_negative_codes` is now `negative_codes_only_ps2_splitters`. New package
checks: `collision_horizontal_rays_match_ps2` and `fallback_no_steep_plane_on_new_only`. Test: `test_ps2_splitter_keeps_no_contact_code`.

**All courses.** Every course has PS2 splitter planes, so every course had the defect. With the earlier build (`keep_splitters=False`, same validator settings as the packages) 988 of 280007 fallback points on the 36 courses got a steep plane on PC only; per course from 6 (France2) to 97 (ItalyM2). After the fix: 0 on every course (table below). All 36 packages in `research-output\course-port-36` were rebuilt with `build_course.py --all` on 2026-10-19 (summary `../course-port/course-packages-36.json`; the render in these packages is the committed one, including the PS2 vertex colour commit). 33 of 36 pass every check. SpainS1 and its flip miss one column (float32 step, below). ItalyS4 misses one horizontal ray: the ray grazes a PS2 solid sliver 0.0009 units long along the ray at a cell corner near |d| = 3200, which is the same float32 inset limit.

**Still open.** Not run in the game. The emulation covers the fallback and the plane codes; the PS2 solid and empty leaf methods
add nothing (`0x236078`, `0x2378B0` are a bare return); the same is assumed for the PC leaf classes (not read). Runtime check for the owner: see
`OWNER-TEST-TURKEY2-WALL.md`.

## Surface grid (tag1400): what it is and how it is built
Found in the data (it was opaque so far):
- **Content.** One record per landscape triangle: its 3 vertices, an index into a string table of material names
  (`$surfacetype(gravel) $shader(ground)...$grnd:gravel_hardNoise Pass`) and the triangle plane. A 20-unit XZ grid lists, per cell, the triangles
  whose XZ bounding box touches the cell.
- **Rule.** Bounds = bounding box of the triangles; cell index in float32; x-major; ascending ids. Rebuilding bounds, dimensions and cells from the
  records gives the retail bytes on 36 of 36 courses (`surface_grid_corpus.py`, `surface-grid-corpus.json`).
  - Double precision was wrong in 3 Italy2 cells.
  - The planes match the float32 recomputation bit for bit on 74 percent of the records and within float32 rounding on the rest.
  - Degenerate triangles keep a NaN plane, as in retail.
- **Source.** The PC record set is the course's visual landscape triangles whose material has `$surfacetype`, with `$detail(...)` removed from
  the name: 22,001 of 23,071 triangles shared with PS2 Turkey3 carry exactly that string. The PS2 grid is therefore built from the PS2 visual
  meshes with `$surfacetype`. The PS2 file has its own surface grid (tag103, 32-unit cells, `$surfacetype` + `$detail` strings); it is a subset
  (22,016 of 27,866 triangles) and is not used directly.
- **Engine use: not reversed.** The loader is at `0x005541D0` (called from `0x551430`); the `$surfacetype(` parser string is used at
  `0x4dbd2c`, called from `0x441b80`. R5T-F.2.1 showed that the tested collision follows the tree and not tag1400. The surface type a wheel
  reads probably comes from here; that is a hypothesis.
- **Record orientation (fixed after the first game test).** PC stores records with a downward plane normal: 97 percent of ground and
  100 percent of water on retail courses. The first build kept the PS2 strip order; in the game that gave splashes on dry ground, a permanent
  "recovering vehicle" on a bridge over water and missing car shadows. Records are now written in PC corner order; Turkey3 has 96.8 percent
  facing down, like retail. See `../track-render1/GAME-TEST-1.md`.
- **Effect of the PS2 grid on Turkey3 columns.** 321 of 16,676 columns change surface type, mostly to `water` (PS2 puddles) and to grass or
  gravel where retail has no record.

## Collision that is not in the landscape BSP (`object_collision_inventory.py`, `object-collision-36.json`)
- **Egg models with their own collision section** (tag101 hull or tag102 cylinder), e.g. checkpoints on both versions, tumbleweeds on PS2. They
  belong to the Egg, not to tag100, and the tree replacement does not touch them. They are lost only if W4 drops the Egg.
- **Static objects inside the PS2 landscape** (houses, caravans, tyres, posts, boats, fences) are solid in the PS2 BSP. The full conversion
  therefore brings them without the T4 brushes. A few PC-only solids disappear because PS2 has no collision there; on Turkey3 that is the
  `stp $shader(metal)` mesh. Per course see the second table.

## Not done / limits
- No game run. Pools sized by the tree header shrink (PS2 trees have fewer nodes than retail), so memory is not expected to grow; load time and
  stability are unknown.
- tag1339 and tag1500 are retail; they must change only when the render changes (W2).
- Exterior shell and void areas are ported on purpose (owner's decision); the retail OFF COURSE logic is still the PC one (W4).
