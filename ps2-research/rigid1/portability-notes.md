# Future PC restoration requirements

The static reverse establishes a reproducible dynamic owner/pose contract for both families. It is sufficient to design a later controller interface with explicit source instance identity, mass/local inertia, convex representation, activation state, position/quaternion/momenta and visual matrix publication. It does not yet supply a faithful full contact solver or demonstrate PC engine integration.

Haybale collision geometry can potentially reuse the existing PC standalone convex asset. Its visual model differs in decoded source triangle count, so visual reuse needs a separate comparison. Baked Italian landscape geometry must be mapped before any replacement; unknown grouping is **COURSE_INSTANCE_MAPPING_REQUIRED**. Contacts and collision ownership of the PC engine remain independently unproved.

Tumbleweed has no named counterpart in the bounded scan. A new scene object and converted model may be needed later, along with renderer-supported treeblend semantics. Shared gravity/RK4 does not justify importing a modern generic rigid engine and claiming exact PS2 parity.

The future controller needs explicit runtime entity/transform access and safe lifetime management. A D3D8 draw wrapper alone does not supply physical scene-instance identity, collision ownership, contacts, sleeping state or the matrix Broker route. **PC_RUNTIME_HOOK / PC_RUNTIME_CONTROLLER** would need separately authorized research and implementation.

A minimal future fidelity test should capture a particular original prop before/during/after contact, read body/shape/material state and compare the same entity world transform. Input constants, restitution/friction mixing, effective clamp configuration and scheduler cadence must be measured before claiming dynamic parity.

No Course SDK, renderer, PC physics, course XML, playable assets or executable was changed in RIGID1.
