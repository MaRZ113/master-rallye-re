# R-SURFACE1 G0 — Vehicle Grime probe

Status: **BUILT, awaiting the owner's run**. Diagnostics only: the probe never changes a draw, a device state or a
game value. Base: `integration/base` 80bc0c1 (renderer `forester-05-pass` b10dc315, owner PASS 2026-11-12).

## What it is

| Part | File |
|---|---|
| Portable core (families, attribution, accumulation dry run, Master Rallye campaign key, store, Service wash entry) | `renderer/vehicle_grime.hpp` |
| Renderer probe (DrawPrimitive observer, per-frame tick, Broker reads, log) | `renderer/vehicle_grime_native.hpp` |
| Call sites (host only; no dependency on Atmosphere being enabled) | `renderer/atmosphere_native.hpp`: `particle_begin` → `observe_particles`, `sun_before_ui` → `tick` |
| Tests | `tests/ps2_diag_tests.cpp` `grime_tests()` |
| Config template | `config/vehicle-grime/VehicleGrime.ini` → `<game>\VehicleGrime.ini` |
| Log analyser | `tools/grime_probe_report.py` |

Independence: the probe reads only `VehicleGrime.ini`. Atmosphere, PS2Port and the Extra Options loader
(`dinput8.dll`) are not involved. Particle handling never depends on the loader. A future EO/Menu Builder toggle may
write this file, but it is not required.

## Signals

* **Surface**: level-0 BGRA SHA-256 of the stage-0 texture at every non-UI DrawPrimitive, compared with
  `grime::kTextures`. The table has hashes of the retail `DataGx/Particles/*.dxt` payloads. The files are a 20-byte
  `0xFEED` header followed by raw BGRA, so the hashes are reproducible offline. Matched families: dust (dirtdust2,
  dirtdust, dustcloud, grassdust, dusty2), mud (newmud, mud), water (watersplash3, watersplash), grass (grassdirt),
  stones (brownstone, greystone), tarmac (smokey).
* **Correction to DESIGN.md**: the six `misc/tracks/<surface>.dxt` textures are byte-identical (black 16×16). Tyre tracks
  can prove wheel contact, but never which surface. The surface comes only from the particles.
* **Car positions**: Broker `Car<N>` → `gaVehicleOutputData` vehicle+0xb0 (ATMOSPHERE6.10 reader). Heading and speed
  come from consecutive positions.
* **Particle geometry**: proxy buffer shadow (`copy_buffer_shadow`) of the dynamic VB, FVF 0x142 stride 24. Each
  triangle centroid goes to the nearest car within `ProbeRadiusCm`. Failures are counted (`shadow_failures`), and the first one is
  logged.
* **Race lifecycle**: the native race HUD context. It stays valid while paused, in replay and in countdown, so pauses do not
  end a race. Paused and replay time does not accumulate. The race ends when the context has been gone for about 60 frames.

## Master Rallye mode persistence (dry run)

The Master Rallye **mode** (not the whole game) keeps its state in Broker values with `SavePlayerState=True`, written
to `DataGame/PlayerState.xml`: `MasterRallye/Stage`, `GameSaved`, `VehicleClass`, `DifficultyLevel`, and
`Car<i>/{CarID, DriverID, Player, TotalTime, RaceTime}` for i < 6. After every race the game returns to the stage
menu (next-stage preview, setup), and the next race starts from a menu button.

* `campaign()` = class + difficulty + (CarID.DriverID) of the six cars. It stays stable for a whole campaign.
* `checkpoint()` = stage + the bit patterns of the six `TotalTime` values. It identifies one saved progress point.
* At race end, the car's grime becomes *pending*. It is bound to the **next different checkpoint** of the same
  campaign. That checkpoint appears when the game updates or saves progress. The store is written atomically to
  `MRRRenderer\grime\master-rallye-grime.txt` (text, one line per car).
* At race start, the grime stored for the current checkpoint is restored, or the car starts clean. So: stage finished →
  saved → game quit → stage loaded again → **same checkpoint → same dirt**. A restart or a quit without a save keeps the
  old checkpoint and its older dirt. A new campaign starts clean.
* **Mode gate and car order**: a race is a Master Rallye mode stage only if its field equals the campaign field. Every
  race `Race/Car<N>/{CarID, DriverID}` must match a distinct `MasterRallye/Car<i>`, and the counts must agree
  (`grime::match_master`). The match also maps race cars to campaign cars, so no order assumption is needed. Attract
  (HUD context `attract`) and replay time never persist.
* Still to be confirmed by the owner run: the Broker tag of the float values (`float_tags`), the `Race/Type` value of
  the mode (attract = 14 seen), and when `PlayerState.xml` is written (`grime_playerstate_written`).
* Service Park groundwork: `CarGrime::wash(fraction)` plus the reserved `[Service] WashFraction`. A partial wash keeps
  the pattern and leaves the car wet.

## Log records (`MRRRenderer\logs\grime-*.jsonl`, 8 MiB cap)

`grime_session`, `grime_texture` (one per texture identity: draw-site RVA, format, size, SHA, family),
`grime_race_start` (Race/Type, replay, race car keys, Master state, restored dry-run grime), `grime_sample` (per car
exposure by family: front/rear/low split, mean particle alpha, dry-run grime), `grime_race_end` (totals, draw-site census,
shadow failures), `grime_master` (Master Rallye state on every change, menus included), `grime_persist_pending`,
`grime_store_loaded`, `grime_playerstate_written`, `grime_shadow_unavailable`.

## Smoke run (2026-11-12, build session, no driving)

Host `host-grime-g0-01`, DLL of the first G0 build: the game boots, the menu works, and the probe writes
`grime_session` and `grime_master` from frame 2. The values are still defaults before the profile load. The menu attract demo
(`Race/Type` 14, 4 cars) produced `grime_race_start`/`grime_race_end`, and `Race/Car<N>/CarID` and `DriverID` are present as Int.
In 1.2 s of attract there were no surface particles. Two fixes came from this run: attract fields entered the persistence
dry run (now gated by the field match and the attract flag), and the per-draw census built a string per draw (about 900 draws per frame;
now an integer key).

Second smoke run (round-2 DLL 6825d6c5, attract demo, about 12 s):

* `particles/dirtdust2` was **matched at the billboard site 0x164ED0**: A8R8G8B8 32×32 managed texture, SHA equal to the offline
  table. The black tyre-track texture was matched at the trail site 0x1722EE, so the tyre tracks are drawn by the trail drawer.
* The buffer shadow of the dynamic particle VB is readable (`shadow_failures` 0).
* Attribution is physically plausible: the leading cars collect dust mostly `rear` + `low`, and a following car collects dust
  `front` (driving in the cloud ahead).
* The attract field is flagged `attract:true`, `master_mode_match:false`, and does not persist.
* Two fixes followed: speed was computed per frame, but the Broker position changes at the physics rate, which gave 0 or
  inflated speeds. Now only distinct positions count. Third run (b623672b): the speed is smooth (19–48 m/s), but dust still saturated in about 4 s.
  A live particle is counted on every frame, so the exposure is particle×frames (5–14 thousand triangles per 0.5 s window,
  about 40 frames). The accumulation now uses the intensity (triangles per frame near the car, `window_frames` in each
  sample), integrated over time. It is calibrated so that a dense trail (about 150–250 triangles per frame) gives about 85 % dust in a minute.

## Owner runs and follow-up fixes (2026-11-12)

Logs: `host-grime-g0-01/MRRRenderer/logs/*-3552.*` (about 9 min) and `*-11504.*` (about 2 min).

* **Probe**: every family matched in game (dust, mud, water, grass, stones, tarmac); `shadow_failures` 0. `Race/Type` is 2 for
  Quick Race, 5 for the Master Rallye mode and 14 for attract. The mode field has 4 cars, while the campaign table has 6 slots (slots
  4–5 are 0/0). The strict count match failed, so nothing persisted. `match_master` now allows unused campaign slots,
  compares readable race slots only and requires the human car to match the campaign player.
* **Stutter caused by the probe**: reading about 40 `MasterRallye/*` keys cost 6.3 ms (each `resolve_id` scans the game's
  string pool), twice a second. That was one 17–19 ms frame in every 0.5 s window against an 11.5 ms median. Fix: key→id
  cache (`broker_id`) and no mode polling during a race. Measured after the fix on attract: worst frame per window 13–15 ms,
  probe cost 0.1 ms. The game simulation publishes poses at about 30 Hz, but the drawn car pose changes every frame (the game
  interpolates), so the 30 Hz rate is not a judder source.
* **PS2 HUD lost in a Master Rallye stage** (not R-SURFACE1): `HudDamageFeedReader` resolved the player ids once per race
  generation. A stale `Race/Car<N>/PlayerType` slot beyond `Race/NumCars` was an unpublished record, so the reader returned
  `player_type_unreadable` and kept that for the whole race. Fix in `ps2_hud_damage_feed.hpp`: only the `Race/NumCars` slots
  decide, and a failed resolution is retried (every 60 calls, at most 20 times per race; the map ids the same way).
* **Add-on cars not darkened at sunset** (not R-SURFACE1): `Atmosphere/vehicles/vehicles.blm` only lists retail families, so
  the Atmosphere body path rejects add-on cars. The material registry was rebuilt with `tools/atmosphere_vehicle_lighting.py`
  from the same inputs plus the add-on resource root: 1342 records, every add-on family qualified. It is a content
  change, not a code change.

## Second owner run and follow-up (2026-11-12, base 439bc19)

Logs: `host-grime-g0-01/MRRRenderer/logs/*` 17:15–17:38 (DLL forester-damage-06 8aaf6ac9 = grime-g0-fix2 + Forester damage).

* The PS2 HUD stayed visible, and add-on cars were darkened at sunset with the rebuilt registry.
* **Add-ons are now universal** (no registry rebuild needed for new PC add-on cars): `BodyMaterials::native_capability`
  falls back to `derived_role()` for a family that the registry does not list at all. `derived_role()` is a C++ port of
  `tools/atmosphere_vehicle_lighting.py` `role_for()` (opaque case; the call site has already certified an opaque draw) and is
  checked by `safe()`. Parity was checked on all 474 (primary, secondary, part, role) combinations of the 1342-row registry,
  with 0 mismatches. Families in the registry keep their authored decisions. Atmosphere ini `BodyMaterialsAddons=1` (default) / `0`.
  `atmosphere_body_material` records carry `capability_source` (`registry` / `addon_naming_contract`). Limitation: PS2-format
  add-on bodies are keyed by texture pixel SHA, have no texture names, and still need the registry.
* **Stutter remained**, but frame times were even (worst frame per 0.5 s window 10–19 ms, none above 25 ms). The cause is
  presentation, not frame time: the 180 Hz display, uncapped ~100–125 fps and the game's SmoothTime clock give uneven time on
  screen per frame. Fix: display-locked frame pacing, see `docs/perf-pacing1/PACING.md`.
